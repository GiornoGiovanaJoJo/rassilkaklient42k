# Сервис рассылок

Веб-приложение для email-рассылок: списки получателей, шаблоны писем,
кампании с расписанием, отписка и учёт открытий.

Стек: FastAPI, SQLAlchemy, Celery, PostgreSQL, Redis. Всё поднимается одним
`docker compose` — внешних зависимостей у стенда нет.

## Что нужно от вас для запуска

1. **Сервер** — Ubuntu или Debian, 2 ГБ памяти и больше.
2. **Доступ по SSH** — адрес, порт, логин, пароль. Ключ не нужен: деплой
   ходит по паролю.
3. **Почтовые ящики** — хост, порт, логин и пароль для отправки.

Лицензионный ключ не нужен: в этой сборке проверка выключена.

## Порядок запуска

### 1. Подготовить сервер

```bash
curl -fsSL https://get.docker.com | sh
```

Больше ничего ставить не нужно: база, Redis и само приложение приедут
контейнерами.

### 2. Прописать доступы в GitHub

`Settings` → `Secrets and variables` → `Actions` → `New repository secret`:

| Секрет | Что это | Обязателен |
|---|---|---|
| `SSH_HOST` | адрес сервера | да |
| `SSH_USER` | пользователь (обычно `root`) | да |
| `SSH_PASSWORD` | пароль | да |
| `SSH_PORT` | порт SSH, если не 22 | нет |
| `APP_ENV` | содержимое `.env` целиком — см. `.env.example` | нет |
| `DEPLOY_PATH` | куда класть код; по умолчанию `/opt/rassilka` | нет |
| `PUBLIC_BASE_URL` | внешний адрес сервиса — нужен только для ручной диагностики | нет |

Пока первые три не заданы, деплой не запускается: проверка кода проходит,
а выкатывать некуда — красного креста на пустом месте не будет.

### 3. Настроить окружение

Настройки живут в секрете `APP_ENV`: деплой кладёт его содержимое в `.env` на
сервере перед запуском. Так они не теряются при переустановке сервера и
правятся в одном месте.

За образец — `.env.example`. Обязательное: `DJANGO_SECRET_KEY`,
`POSTGRES_PASSWORD`, `PUBLIC_BASE_URL`, `CBMAIL_ADMIN_LOGIN`,
`CBMAIL_ADMIN_PASSWORD`; ящики — блоками `CBMAIL_SMTP_1_*`, `CBMAIL_SMTP_2_*`.

`PUBLIC_BASE_URL` — адрес, по которому сервис виден **снаружи**: по нему
строятся ссылки отписки в письмах, и получатель открывает их из интернета.

Если `APP_ENV` не задан, деплой оставляет `.env`, который уже лежит на сервере,
— так можно вести настройки вручную:

```bash
cd /opt/rassilka && cp .env.example .env && nano .env
```

### 4. Выкатить

Push в `main` либо `Actions` → `CI/CD` → `Run workflow`.

Деплой соберёт образ, поднимет базу, Redis, веб и воркер, создаст схему,
первого администратора и почтовые профили, дождётся ответа от сервиса и
**проверит авторизацию на почтовом сервере по каждому ящику** — отдельной
строкой в журнале.

### 5. Войти

`http://<адрес>/` под логином и паролем из `CBMAIL_ADMIN_LOGIN` и
`CBMAIL_ADMIN_PASSWORD`. После первого входа пароль стоит сменить в профиле, а
переменные из `APP_ENV` убрать — учётная запись останется.

### Почтовые ящики

Описанные в окружении ящики заводятся при установке — хост, порт, логин,
пароль и адрес «От кого» не нужно перепечатывать в интерфейсе.

Уже заведённый профиль повторная выкатка **не трогает**: иначе пароль,
исправленный в интерфейсе, откатывался бы к значению из `APP_ENV` при каждом
перезапуске. Признак совпадения — пара «владелец + логин ящика».

Порт и способ шифрования должны совпадать: `ssl` — это 465, `tls` — 587.
Связка «465 + STARTTLS» не отвечает ошибкой, а висит до таймаута, потому что
сервер ждёт TLS-рукопожатие с первого байта.

Почтовые сервисы (Mail.ru, Яндекс, Google) для внешних программ требуют
**отдельный пароль приложения** — обычный пароль от входа на сайт к SMTP не
подходит. Если в журнале деплоя ящик помечен `[НЕТ]` с отказом авторизации,
дело почти всегда в этом.

### Лицензия

Проверка ключа в этой сборке выключена — сервис работает без лицензии. Код
проверки не вырезан: он включается переменной `LICENSE_REQUIRED=1`, но тогда на
сервере должен лежать `license.key`, выпущенный под его `machine-id`, иначе
сервис отдаёт 503 на всё, кроме страницы активации.

## Чем отличается от gn-mailer

Код тот же, развёртывание — нет. Прежний вариант рассчитан на сервер, где уже
крутится старый стек: он подключался к чужой сети Docker и к готовым
контейнерам базы и Redis, а схему базы ему оставили Django-миграции прошлой
версии.

Здесь всё своё и разворачивается с нуля:

* `docker-compose.yaml` поднимает базу и Redis сам, наружу их не публикуя;
* на пустой базе схема создаётся целиком из моделей — раньше сервис
  стартовал и падал на первом запросе, потому что таблиц не было;
* первый администратор заводится из `.env` — иначе войти было некому:
  пользователей в системе создаёт только существующий администратор;
* почтовые ящики заводятся оттуда же, а деплой проверяет по ним авторизацию;
* проверка лицензии выключена: ключ привязан к `machine-id`, и переустановка
  сервера гасила бы сервис до выпуска нового.

## Обслуживание

**Журналы:**

```bash
cd /opt/rassilka && docker compose logs -f web
```

**Перезапуск:**

```bash
cd /opt/rassilka && docker compose restart web worker
```

**Диагностика** — `Actions` → `Diagnostics` → `Run workflow`. Ничего не меняет:
показывает доступность, состояние отписок, SMTP-профили и последние кампании.

**Очистка общего стоп-листа** — `Actions` → `Stoplist clear`, с подтверждением.
Общий стоп-лист блокирует адрес у всех отправителей; адресные отписки живут
отдельно и этим действием не затрагиваются.

## Разработка

```bash
cd app
pip install ".[dev]"
pytest -q
ruff check .
```

Тесты и линтер гоняются на каждый push — деплой идёт только после зелёных.
