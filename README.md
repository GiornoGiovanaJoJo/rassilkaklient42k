# Сервис рассылок

Веб-приложение для email-рассылок: списки получателей, шаблоны писем,
кампании с расписанием, отписка и учёт открытий.

Стек: FastAPI, SQLAlchemy, Celery, PostgreSQL, Redis. Всё поднимается одним
`docker compose` — внешних зависимостей у стенда нет.

## Что нужно от вас для запуска

1. **Сервер** — Ubuntu или Debian, 2 ГБ памяти и больше.
2. **Доступ по SSH** — адрес, порт, логин, пароль. Ключ не нужен: деплой
   ходит по паролю.
3. **Файл лицензии** — ключ выпускается под конкретный сервер (см. ниже).

## Порядок запуска

### 1. Подготовить сервер

```bash
curl -fsSL https://get.docker.com | sh
```

Больше ничего ставить не нужно: база, Redis и само приложение приедут
контейнерами.

### 2. Прописать доступы в GitHub

`Settings` → `Secrets and variables` → `Actions` → `New repository secret`:

| Секрет | Что это | Обязателен |
|---|---|---|
| `SSH_HOST` | адрес сервера | да |
| `SSH_USER` | пользователь (обычно `root`) | да |
| `SSH_PASSWORD` | пароль | да |
| `SSH_PORT` | порт SSH, если не 22 | нет |
| `DEPLOY_PATH` | куда класть код; по умолчанию `/opt/rassilka` | нет |
| `PUBLIC_BASE_URL` | внешний адрес сервиса — нужен только для ручной диагностики | нет |

Пока первые три не заданы, деплой не запускается: проверка кода проходит,
а выкатывать некуда — красного креста на пустом месте не будет.

### 3. Настроить окружение на сервере

```bash
cd /opt/rassilka
cp .env.example .env
nano .env
```

Заполнить обязательное: `DJANGO_SECRET_KEY`, `POSTGRES_PASSWORD`,
`PUBLIC_BASE_URL`, `CBMAIL_ADMIN_LOGIN`, `CBMAIL_ADMIN_PASSWORD`.

`PUBLIC_BASE_URL` — адрес, по которому сервис виден **снаружи**: по нему
строятся ссылки отписки в письмах, и получатель открывает их из интернета.

Файл `.env` на сервере деплой не трогает — он не входит в передаваемый архив.

### 4. Выкатить

Push в `main` либо `Actions` → `CI/CD` → `Run workflow`.

Деплой сам соберёт образ, поднимет базу, Redis, веб и воркер, создаст схему и
первого администратора, дождётся ответа от сервиса и покажет состояние
лицензии.

### 5. Активировать лицензию

Ключ привязан к конкретной машине, поэтому при переезде на новый сервер нужен
новый ключ. Порядок:

1. открыть `http://<адрес>:8002/license` — там показан `host_id` сервера
   (его же печатает деплой в журнале);
2. выпустить ключ на этот `host_id`;
3. вставить ключ на той же странице.

До активации сервис закрыт целиком, кроме страницы активации. Это ожидаемое
поведение, а не поломка: health отвечает, но войти нельзя.

### 6. Войти

`http://<адрес>:8002/` под логином и паролем из `CBMAIL_ADMIN_LOGIN` и
`CBMAIL_ADMIN_PASSWORD`. После первого входа пароль стоит сменить в профиле, а
переменные из `.env` убрать — учётная запись останется.

## Чем отличается от gn-mailer

Код тот же, развёртывание — нет. Прежний вариант рассчитан на сервер, где уже
крутится старый стек: он подключался к чужой сети Docker и к готовым
контейнерам базы и Redis, а схему базы ему оставили Django-миграции прошлой
версии.

Здесь всё своё и разворачивается с нуля:

* `docker-compose.yaml` поднимает базу и Redis сам, наружу их не публикуя;
* на пустой базе схема создаётся целиком из моделей — раньше сервис
  стартовал и падал на первом запросе, потому что таблиц не было;
* первый администратор заводится из `.env` — иначе войти было некому:
  пользователей в системе создаёт только существующий администратор.

## Обслуживание

**Журналы:**

```bash
cd /opt/rassilka && docker compose logs -f web
```

**Перезапуск:**

```bash
cd /opt/rassilka && docker compose restart web worker
```

**Диагностика** — `Actions` → `Diagnostics` → `Run workflow`. Ничего не меняет:
показывает доступность, состояние отписок, SMTP-профили и последние кампании.

**Очистка общего стоп-листа** — `Actions` → `Stoplist clear`, с подтверждением.
Общий стоп-лист блокирует адрес у всех отправителей; адресные отписки живут
отдельно и этим действием не затрагиваются.

## Разработка

```bash
cd app
pip install ".[dev]"
pytest -q
ruff check .
```

Тесты и линтер гоняются на каждый push — деплой идёт только после зелёных.
